\chapter{Introducción}

\section{Contexto}

DNS (Domain Name System) es un protocolo fundamental para el funcionamiento de la capa siete del modelo OSI, permitiendo que un usuario pueda 
acceder a una IP global a través de un nombre de dominio, como por ejemplo \texttt{dcc.uchile.cl.} Para lograr esto existen 2 actores principales: 
el Resolver y el Name Server.

El Resolver es el programa encargado de tomar una consulta de un nombre de dominio desde un dispositivo como un computador o un celular y 
transformarlo en una consulta DNS, la cual es un mensaje en bytes con una estructura definida por el protocolo DNS, con las siguientes 5 
secciones: Header, Question, Answer, Authority y Additional

El Name Server es el que conoce las IP de los dominios y es el encargado de responder las consultas DNS que envía el Resolver, pero este proceso
no es sencillo y requiere del arduo estudio y programación de los RFC (Request For Comments), documentos estandarizados de cómo debe funcionar 
el internet.

En este contexto, el área de investigación de NIC Chile (NIC Labs) implementó una librería de funciones para DNS en el lenguaje Rust, como 
caso de prueba de dicha librería desean implementar un servidor de nombres (Name Server) DNS que utilicen para su propia zona \texttt{niclabs.cl.}
Una zona es un conjunto de nombres de dominios hijos de un dominio padre, en este caso el dominio padre es \texttt{niclabs.cl.} (la zona misma) y un dominio hijo podría ser 
\texttt{a.niclabs.cl}

La librería DNS-RUST  de NIC Labs sigue cabalmente las indicaciones de los RFC sin implementar ningún tipo de optimización que no sea 
referenciada por ellos, por lo que es importante la implementación del Name Server bajo esas especificaciones ya que puede ser utilizado 
más adelante para investigación y desarrollo.

Mencionar que la librería \texttt{dns-rust} es solo una herramienta que contiene las funciones necesarias para transformar un mensaje DNS en bytes a 
una estructura en Rust (parse), un Cliente y un Stub-Resolver, es decir, no posee nada relacionado a un Name Server. De esta manera todas las 
funcionalidades, estructuras de datos y algoritmos serán implementados desde cero. 

Como se verá más adelante, implementar un Name Server con todas sus funcionalidades incluyendo las que aún no posee la librería es un trabajo 
que toma más de un semestre, de hecho, para tener más contexto, el Stub-Resolver de la libería DNS-RUST fue desarrollado por años de manera 
grupal, por lo que es lógico pensar que su contraparte (un Name Server) no puede ser completado al cien porciento por una sola persona en un 
semestre, provocando así que el trabajo a realizar sea acotado sólo a las funcionalidades de DNS Security Extension, Extension DNS 0, 
creación de estructuras de datos basadas en el \texttt{masterfile}, implementación del algoritmo de búsqueda del Name Server y conexiones UDP-TCP 
asíncrónicas.



\section{Glosario}
Antes de continuar con el desarrollo de este informe, es necesario abarcar ciertos conceptos fundamentales que se utilizarán en las secciones posteriores:

\begin{itemize}

    \item \textbf{Stub-Resolver}: Resolver simple que delega completamente el trabajo a un resolver recursivo externo. Estos resolvers recursivos suelen ser complejos y, en la práctica, un 
           stub-resolver utiliza servicios de grandes proveedores como Google o Cloudflare.

    \item \textbf{Extension DNS 0 (EDNS0)}: Primera gran extensión del protocolo DNS. Añade nuevas funcionalidades, entre ellas la posibilidad de ampliar el tamaño máximo de los mensajes DNS 
          (consultas y respuestas), superando el límite tradicional de 512 bytes.

    \item \textbf{DNS Security Extension (DNSSEC)}: Extensión de seguridad del protocolo DNS que permite incorporar firmas digitales y realizar validación criptográfica de la información 
          contenida en los Resource Records.

    \item \textbf{Resource Record (RR)}: Unidad básica de información en DNS. Cada RR representa un dato asociado a un nombre de dominio y tiene un tipo específico con su propia estructura.

    \item \textbf{RRset}: Conjunto de RR que comparten el mismo nombre de dominio, clase y tipo.

    \item \textbf{Catálogo}: Estructura jerárquica que contiene las zonas administradas por el Name Server.

    \item \textbf{Árbol de dominios}: Estructura jerárquica que almacena los RRsets asociados a los dominios que maneja el Name Server.

    \item \textbf{Tipos de Resource Records clásicos}:
        \begin{itemize}
            \item \textbf{Answer (A)}: Contiene la dirección IPv4 asociada al nombre de dominio solicitado.
            \item \textbf{Name Server (NS)}: Indica el nombre de dominio del servidor autoritativo responsable de una zona.
            \item \textbf{Canonical Name (CNAME)}: Alias que redirige un nombre de dominio a otro nombre canónico.
            \item \textbf{SOA (Start of Authority)}: Contiene información administrativa sobre la zona, como el servidor principal, el correo del administrador, 
                  números de serie y tiempos de actualización.
            \item \textbf{Optional (OPT)}: RR especial introducido por EDNS0. Su función más relevante es permitir aumentar el tamaño máximo de los mensajes DNS más allá del límite clásico de 
                  512 bytes.
        \end{itemize}

    \item \textbf{Tipos de Resource Records de DNSSEC}:
        \begin{itemize}
            \item \textbf{DNS Public Key Record (DNSKEY)}: Contiene la clave pública utilizada para validar firmas digitales en un RRSIG.
            \item \textbf{Resource Record Signature (RRSIG)}: Firma criptográfica generada con la clave privada del servidor autoritativo, y que autentica un RRset completo.
            \item \textbf{Delegation Signer (DS)}: Hash de la clave pública contenida en un DNSKEY, almacenado en la zona padre para validar la delegación.
            \item \textbf{Next Secure Record (NSEC)}: Indica el siguiente nombre válido en el orden canónico dentro de la zona y enumera qué tipos de RR existen para un dominio. 
                   Se utiliza en pruebas de no existencia.
        \end{itemize}

    \item \textbf{Clase de un RR}: Valor que determina el contexto o protocolo asociado. Normalmente es \texttt{IN} (Internet), aunque existen otras clases menos utilizadas.

    \item \textbf{RDATA (Response Data)}: Parte del RR que contiene la información específica del tipo correspondiente. Su estructura depende del tipo de RR.

    \item \textbf{Glue Record}: RR especial que contiene la dirección IP de un Name Server delegado en otra zona, utilizado para evitar ciclos infinitos durante la resolución.

    \item \textbf{Wildcard}: Nombre de dominio generalizado que permite responder por múltiples subdominios ausentes, utilizando el símbolo asterisco (*). Por ejemplo, 
           \texttt{*.niclabs.cl} puede responder consultas como \texttt{a.niclabs.cl} o \texttt{b.c.niclabs.cl}.

    \item \textbf{NXDOMAIN}: Código de error que indica que el nombre de dominio consultado no existe en la zona.

    \item \textbf{NO\_DATA}: Código de error que indica que el nombre de dominio consultado sí existe, pero no posee registros del tipo solicitado.
    
    \item \textbf{Formato canónico}: Representación estandarizada de los datos de un RRset utilizada por DNSSEC para firmar y verificar información.
      Consiste en ordenar lexicográficamente los registros y normalizar cada campo, garantizando que la firma criptográfica sea siempre reproducible e independiente del orden 
      original de los datos.


\end{itemize}

\section{Objetivos}

\subsection*{Objetivo General}

El objetivo de este trabajo de título es construir un MVP (Producto Mínimo Viable) de un Name Server Autoritativo Iterativo capaz de controlar la zona de 
dominio del laboratorio de manera segura, eficiente, siguiendo al pie de la letra los RFC y usando las herramientas de la librería DNS-RUST como 
apoyo.

Que el Name Server sea Iterativo consiste en que su algoritmo busca el nombre de dominio solicitado dentro de su estructura de datos, si no 
tiene la respuesta directa, envía una referencia hacia otro Name Server que si podría tenerla, y si no encuentra ninguna respuesta envía un 
error. La alternativa es un Name Server recursivo que, si no conoce la respuesta a la consulta, utiliza un Resolver interno para averiguarla y 
responder, y que por su diseño y construcción no es parte de este trabajo de título.

\subsection*{Objetivos Específicos}\label{sec:obj-e}

\begin{enumerate}
\item Establecer canales de trasmisión confiables, en los protocolos de UDP y TCP asincrónicos.
\item Responder correctamente a consultas DNS de tipo basico (A, NS, CN) con sus Resource Records correspondientes.
\item Seguir estrictamente lo establecido por los RFC antiguios y actuales.
\item Asegurar seguridad con DNSSEC (DNS Security Extension), usando algoritmos de encriptación, llaves publicas y privadas, firmas y una cadena de autentificación.
\item Crear de estructuras de datos a partir de un \texttt{masterfile} .
\item Conectar las herramientas de la libería \texttt{dns-rust} usando su stub-resolver como cliente y sus parses de mensajes para manejar las consultas DNS .
\item Cumplir con estándares de documentación en el código.
\item Incluir EDNS0 (Extension DNS 0) necesaria para cumplir DNSSEC. Especificamente sabiendo leer y procesar consultas del tipo OPT.

\end{enumerate}
